# 原有 RAG 召回不足的原因分析

仅分析原有 AnswerService/RetrievalService 使用的合并库B基线冻结dev记录。不运行新增研究Agent，不调用模型API，不读取test/holdout，不更改索引、配置、gold或历史结果。以下不是当前线上实时指标，也不是答案正确率。

## 先分清口径

| 指标 | 官方正例 | 仓库正例 |
|---|---:|---:|
| 原B候选完整 | 46/54（85.2%） | 42/50（84.0%） |
| 原B直接Top5完整 | 41/54（75.9%） | 40/50（80.0%） |
| 原B-T5实际正文交付完整 | 43/54 | 40/50 |
| v6冻结实验正文交付完整 | 45/54 | 41/50 |

候选完整要求同一可接受证据组内全部必要片段均进入候选。命中主题、文档或一条必要证据不能代替完整。原Top5可能通过邻接补齐，因此直接Top5与实际正文交付不相同。v6只改变证据选择，候选仍为46/54、42/50，不代表已接入默认服务。

v6剩18个交付失败中，16个候选不完整、2个候选完整但交付失败。后者是预算/选择问题，不属于召回率低。本报告聚焦前16个。

## 1. 每路Top30在进入重排前已经漏掉具体证据

语料16320个text片段；本批B使用BM25 Top30与dense Top30并集，共45～60个候选。16题缺失的标注片段均不在任一通道Top30，候选集合逐题核实等于两路并集；本批没有RRF再次截断造成的额外丢失。重排无法找回候选外片段。

重算全量BM25后，16题的前30顺序与冻结结果全部一致。8题的全部缺失片段位于35～75名，如端侧量化35、Async属性44、前缀共享原理46、抢占恢复67、跨GPU参数75。它们有可能通过增加入口深度被发现；仍需受总候选预算限制，不能据此保证交付改善。

另一方面，LoRA缓存身份片段排246/444，KV公式排332/1263，跨vLLM/SGLang分离阶段条件排1049/1389。把30改60无法解决这些问题，继续提高到上千也会带来大量无关候选。

## 2. 查询措辞与原文术语、参数、公式对不上

同一额外哈希片段在直接问哈希组成时可以召回；问“两个适配器同文本能否共享”时，问题的adapters/share与证据中的LoRA IDs/Extra hashes/unique不是相同表达。

原英文BM25分词没有词干/词形归一化：recomputation/recomputed、disaggregation/disaggregated是不同词。中文自然描述与combine、tensor_parallel_size、KV_bytes、num_kv_heads等也缺少统一的检索别名。参数和下划线标识作为整体token保留，数值公式缺少问句中的自然语言。

BM25可机械确认这些词项差异；dense Top30也未补上缺口。当前小型中文BGE对混合语言、关系与符号的能力可能相关，但本轮没有模型替换对照，不能把全部缺口归因于embedding模型。

## 3. 子块有事实，但缺少定位它所需的上下文

14/16题已经召回了所有缺失证据所在文档的其他片段，往往连同父块的其他子块也已进入候选。主要问题不是资料未入库，而是文档内没有定位到具体条件或公式。

原dense索引编码正文；BM25包含正文和标题，但未统一加入文件名、产品/版本、前文关系。CUDA Async限制句的heading为空；KV公式被保留为代码子块，定义说明在相邻正文；SGLang句子“resolves these … separating the two stages”依赖前文指代。

结构清洗保留正文和定位，保证了证据可追溯，但不自动保证短条件、代码公式与前文关系适合检索。事实片段短，也可能因概述或同主题资料占据候选前列而落选。

## 4. 单条整问检索容易丢跨文档的第二个要求

official-005-4同时问抢占恢复成本和跨GPU拆分参数，原B已有恢复相关证据，却缺tensor_parallel_size的片段。旧子问题补召回Q5补齐该题；单纯加深D5没有补齐该题。

official-008-4同时依赖SGLang阶段作用与vLLM吞吐限制，两份标注正文都缺。已有子问题策略仍未补齐，说明“拆问题”本身不足，还要保留各子问题的产品、版本与术语身份，且最后保证每项条件有候选。

## 5. 稀疏gold让部分真实检索被记作失败

合并库包含多个来源的相似解释，旧gold主要绑定特定来源/片段。repo-016-2标注MoE章，但实际交付的“06-超节点”正文明确描述dispatch派发、combine回原卡；repo-018-1标注量化章，但实际交付的handbook正文明确描述SmoothQuant等价变换与激活到权重的迁移。

这些是值得独立审核的替代证据，不是本轮重新判为成功。KV公式题也召回了其他来源的因子解释，仍需核对公式正文和全部必要条件是否真的交付；不能只凭主题相关就算完整。GQA题的rubric包含MQA内容，而问句侧重GQA，也应核对评分范围。

因此，16个候选不完整不能解释成16个答案必错，不能宣称真实语义召回率只有84%。本轮不事后修改gold或重算成绩。

## 已有实验能支持什么

| 方法 | 官方完整候选 | 仓库完整候选 | 相对B的得失 |
|---|---:|---:|---|
| B原候选 | 46/54 | 42/50 | — |
| D加深候选 | 48/54 | 44/50 | 恢复4题，无候选退化 |
| Q子问题补召回 | 47/54 | 44/50 | 恢复3题，无候选退化 |
| L只增强词法检索视图 | 47/54 | 44/50 | 恢复4题，丢1题 |
| E只增强dense检索视图 | 47/54 | 43/50 | 恢复3题，丢1题 |
| LE两路增强检索视图 | 46/54 | 44/50 | 恢复5题，丢3题 |

至少一种旧对照能补齐16题中的6题，其余10题在这些对照中仍未补齐。候选更完整不保证最终交付更完整，增加到Top8交付也不改变候选召回。不能把不同方法的恢复题相加当成一个可部署配置。

## 改进优先级

1. 独立审核现有替代证据与题目/rubric范围，把标签漏计与真正缺必要事实区分开；另建标签版本，原冻结成绩不改写。
2. 在原检索服务中比较候选深度及技术词处理，保留原候选通道，控制总候选、延迟及交付预算。优先验证35～75名的条件段能否有效补入。
3. 为条件句、代码/公式建立含产品、版本、标题和相邻定义的检索视图，答案仍使用原文；分别比较词法和dense，避免同时改变所有因素。
4. 跨文档问题在原链路内做受限子问题补召回，并独立验证各条件覆盖。继续以原有问答链路为主，不重新引入新增研究Agent。

## 证据与复现

[逐题缺失片段、完整BM25名次和旧对照](diagnostics.json)。诊断重现16条BM25 Top30，核验127份源文件hash。16题对应12个不同缺失片段，存在同事实不同问法的相关性，不作为16个独立失败机制。

复现：`uv run python scripts/analyze_original_rag_recall.py --output evals/merged-corpus-v2/<new-diagnosis-directory>`。此脚本只读dev冻结结果，输出到全新目录，0生成/embedding/重排模型调用，0索引写入。
